## 2. Purpose, scope, and expected value

The intended outcome is faster, predictable evidence preparation and commit-message production for large change sets while preserving exact selected units, canonical bytes, diagnostics, security checks, and recovery behavior.
The user-visible objective is reduced waiting for trustworthy local workflows, not a microbenchmark score in isolation.
Selection indexing has the strongest reported benefit and should lead implementation after the baseline is qualified.
Coverage reuse is second, followed by carefully qualified distribution traversal improvements.
Digest reuse, EOF scratch-buffer reuse, conformance concurrency, and new telemetry remain conditional on measurements and their own acceptance decisions.

In scope:

- Exact and prefix selector costs, evidence-plan/catalog consumers, and structured message finalization.
- Repeated semantic coverage resolution within one structured bulk rendering operation.
- Directory inventory sorting and repeated ancestor checks during build/distribution.
- Repeated canonical manifest digest computation and stable-file EOF allocation where material.
- Deterministic conformance runtime, bounded subprocess concurrency, and retained failure evidence.
- Reproducible benchmarks, deterministic cost contracts, performance acceptance, and optional local phase timing.
- Generated consumer validation, migration/recovery analysis, review, and authorized release handoff.

Non-goals:

- HTTP/server/browser/database optimization: the inspected workload is an offline CLI and toolchain; no production HTTP/APM evidence was supplied.
- Changing selection meaning, commit approval, Git signing, publication authority, transaction safety, or evidence identities to gain speed.
- Editing generated `skills/` or `plugins/` payloads directly, editing installed copies, or reformatting historical evidence/evaluation fixtures.
- Introducing worker threads around synchronous Git commands, custom JavaScript byte-comparison loops, a new cache service, or a new benchmark framework without demonstrated need.
- Running real model evaluations or adopting dependencies/tool versions as part of this document synthesis.
- Unrelated retained-work cleanup or changes to consumer repositories.

### 3.6 Corrections and limitations that affect implementation

1. The current selector does perform the nested scan described by HOT-01.
   For 1,000 exact path selectors and 1,000 path-bearing units, the source's one million comparisons and roughly two million buffer constructions describe allocation traffic, not two million simultaneously live buffers or quadratic retained memory.
   Index lookup cost includes total encoded path bytes and returned matches; `O(N + M)` assumes bounded field count, byte lengths, and match volume.
   Prefix matching remains `O(P * N)` comparisons for P prefixes unless a separate prefix algorithm is justified.
2. The ties harness currently uses `src/group-${index % 4}/.../same.txt`, so 1,000 units have four distinct destination paths, not the audit's claimed one path.
   The lower selector count supports the causal hypothesis but is not by itself a complete complexity proof.
   Duplicate-destination ties are a sorting stress case; the harness deliberately omits rendering for ties with more than one unit.
3. Coverage duplication occurs in the structured bulk inventory path, not universally in all detailed or externally supplied messages.
   A ratio of catalog and render timings cannot alone attribute 50% of cost to the second pass.
   Direct callers of `validateApprovedMessage` remain validation boundaries.
4. Patch 2 replaces byte comparison with JavaScript string `<`/`>` comparison while calling it UTF-8 ordering.
   That does not preserve the repository's byte-order contract for all Unicode names.
   Existing `performance-ordering.test.mjs` explicitly covers supplementary characters and UTF-8 versus UTF-16 ordering.
   Preserve byte ordering with prepared byte keys; do not copy this part of Patch 2.
5. A cached path string proves only a past observation.
   The proposed Set can suppress a later ancestor recheck after replacement/redirection, and even adds nonexistent paths to its cache.
   It also exposes a caller-supplied verified Set in exported function signatures.
   Operation-scoped storage alone does not resolve these issues.
   Do not adopt the proposed cache without a reviewed freshness/identity contract and adversarial evidence.
6. `manifestDigest` already returns a supplied 64-character lowercase digest, and workflow callers already attach snapshot digests in several places.
   Synthetic manifests without that property may overstate production fallback cost.
   Prove which digest definition each producer owns; a canonical logical-manifest digest and stored-file-byte digest are not interchangeable by assumption.
7. The existing in-memory harness explicitly says no elapsed-time assertion belongs in `node:test`.
   The audit's proposed 15 ms single warmup/single sample test is therefore a benchmark-budget proposal, not a test to paste into the suite.
   It asserts elapsed time and output count; despite the audit's description, it contains no allocation assertion.
8. The current expensive 1,000-unit catalog/render measurements use one timed iteration after one warmup.
   They motivate work but do not establish a reliable percentile or universal CI threshold.
   The signed workflow harness exercises `workflow commit --message`; it is a safety/integration journey, not proof that it traverses the same structured bulk rendering hotspot.
9. `check-conformance.js` uses a fake local engine and static providers, plus portability, installation, bridge, and consumer-process checks.
   It is not a real multi-agent/model evaluation campaign.
   Its native validate/run pair is sequential, with per-command 45-second timeouts; the bridge subprocess has a 90-second timeout.
   The proposed global 60-second limit requires evidence and approved policy changes, not removal of correctness coverage.
10. The audit reports 25/25 selection and 9/9 ordering tests passing, but also records failed builds, temporary experiments, and restoration of source/generated files.
    There are no retained raw results in the supplied document to establish final qualification, reasons for build failure, or the exact combined test invocation behind those counts.
    Do not repeat the audit's Git restoration method: this repository requires targeted reversal of task-owned edits and preservation of other working changes.

### 4.1 Domain invariants

- Canonical nonempty manifests retain unique `F` plus six-digit IDs and existing validation order.
- Selector normalization remains authoritative: unknown fields, duplicate values, invalid relative paths/prefixes, and invalid combinations fail as before.
- `all` returns a fresh array in manifest order; `remaining` respects the supplied assigned-ID Set and preserves its empty-result failure.
- Exact destination/source matches use authoritative encoded path bytes when present; source selectors apply only to renamed units.
- Multiple units sharing a path or kind remain matched; mixed selectors form a union; output follows manifest order, not Map order or selector order.
- Unmatched diagnostics retain field/value ordering, total count, the 32-entry cap, the 256-byte value bound, long-value index/byte-length representation, omitted count, and recovery instructions.
- Evidence/domain partitions remain exhaustive and nonoverlapping; rationale/file-note overlap rules and final `remaining` placement remain unchanged.
- Commit message bytes, catalog/capsule bindings, canonical ordering, schema versions and approved-message rejection behavior stay identical unless a separately accepted observability change explicitly defines another surface.
- Filesystem checks continue rejecting links/nonregular inputs as required; no externally populated cache, weaker stable-read contract, or silent fallback becomes authority.
- Deterministic conformance, model behavior, live host activation, release readiness, and publication remain separate claims.

### SLICE-004: Reduce distribution inventory overhead with preserved trust

**Outcome:** Build inventory returns the same ordered paths/bytes and refuses unsafe inputs with less avoidable work.

Profile `existsSync`, `lstatSync`, directory reads, and filename-key construction separately.

Treat ancestor memoization as a separate security decision within this slice.
