# Windows integrated bridge qualification

The Windows Job Object host and independent closure recorder have an integrated synthetic-provider contract test at `tests/scripts/windows-assured-bridge.test.mjs`. It supplements the isolated process-host tests, explicit interrupted-home recovery tests and normal transport/equivalence fixture. On 2026-10-05 the owner approved the Windows x64 qualification marker `assured-qualified` for this bound `windows-job-v2` path. It permits explicitly selected dispatch; real model calls retain exact packet authorization. This qualification does not authorize client activation, OS-level egress claims, automatic or real-home recovery, or Linux cutover.

The test runs the pinned native skill-up executable, the actual Python host and bridge, the maintained Git suite and Hadden runtime, and a synthetic Codex App Server. It creates a disposable plain checkout with a test-only qualification override and disposable credential-free homes. It verifies the production manifest's bytes are unchanged. The normal `npm test` glob includes the test; non-Windows hosts report an explicit skip.

## Proof and independent observations

The provider proxy pauses at the first actual `turn/start`. Before interruption, the observer requires persisted consumption and an execution lease, inventories the prepared job through Windows APIs, and verifies that the synthetic provider and grandchild are members. Process identity records include executable image, PID, parent PID and losslessly encoded creation FILETIME.

Native custom-engine execution inserts Git Bash intermediaries. The test identifies the native consumer by its pinned executable image, the bridge by the provider's recorded parent, and the host by the consumer's parent, bound interpreter image and wrapper ancestry. It does not assume that the bridge's immediate parent is skill-up. The observer closes its query-only job handle before interruption so it cannot extend the job's lifetime. Microsoft's [Job Object contract](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) and [process creation attributes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) define the kernel boundary.

| Scenario | Required result |
| --- | --- |
| Normal completion | Two controller turns, sealed completed Hadden outcome, completed home history, no live lease or observed surviving job member |
| Mismatched exact authorization | No provider turn or consumed launch; attempted carrier cannot replay |
| Wrapper, host, consumer or bridge abrupt death | Observed job members close within the fault's eight-second observation bound; consumed attempt bytes remain unchanged; no fabricated terminal outcome; eligible interrupted execution leases require explicit state-bound recovery |
| Recorder abrupt death | Host revokes the workload; observed members close; missing independent signed recovery proof remains unknown and the lease is retained |
| Simultaneous host/recorder death | Last-handle-close retains kernel containment; observed members close, but missing signed proof remains unknown and the lease is retained |
| Requested consumer cancellation | Windows SIGINT terminates the consumer; the same closure, consumption and retained-lease obligations apply |
| Provider abrupt death | Truthful failed Hadden outcome with `provider-failed`; no surviving observed job member |
| Provider deadline | Truthful failed Hadden outcome with `timed-out`; existing preparation/native budgets remain unchanged; no surviving observed job member |

Concurrent wrapper attempts and subsequent replays are refused. Interrupted consumed sessions are also presented directly to the maintained execution API once: its existing evidence gate rejects `attempt.json`, without launching a provider or resetting a lease. This is a refusal test, not execution fallback. PIDs that remain present fail conservatively, including potential reuse; the observer does not treat a different process as safe to terminate.

The isolated host suite remains responsible for missing APIs, invalid invocation, nested jobs, creation-time parent loss, inherited pipes and spawn races. Integrated post-consumption scenarios contain a real descendant and grandchild with inherited output handles. The revised host arms the independent recorder before workload creation, pins exact job/producer/consumer/packet association and native process birth identities, and retains a signed zero-active closure receipt after host termination. Unknown closure never becomes a successful Hadden result. These tests do not prove every possible startup interleaving or OS-level network isolation.

Original receipts, failed evidence and review admissions are retained under `C:/Users/maksy/.hi/w/e/operator-evidence/2026-10-05-evaluation-home-recovery/`.

The current disposable negative control sets `WINDOWS_BRIDGE_FIXTURE_SCENARIO=host-death` and `WINDOWS_BRIDGE_FIXTURE_FAULT=omit-recorder-termination`. Removing the recorder's explicit termination must fail the signed zero-active closure-proof requirement. Eventual kernel termination when the last handle closes does not retroactively satisfy that proof. The default repository verification sets neither fixture variable and exercises all eleven integrated scenarios.

Kernel workload closure, resource recovery and Hadden completion are distinct. Abrupt termination can close every job member while leaving an incomplete run and execution lease. The explicit recovery API verifies the original versioned lease/journal, exact signed closure binding, consumed attempt, outcome bytes or absence and current generation/credential metadata. It preserves the used generation in quarantine and original lease/journal in separate recovered history, creates a clean marked execution home and transfers at most the validated single-link credential cache without reading its contents. No outcome is invented and no packet regains launch authority. Native recovery tests cover refused live owners, stale/forged/conflicting state, generation substitution, interrupted transitions and exact resumption. Subsequent fresh fixture authority can use the repaired role; original consumed authority still refuses.

See [interrupted evaluation-home recovery](evaluation-runtime.md#interrupted-evaluation-home-recovery) for `prepare-recovery`, `apply-recovery` and `resume-recovery` commands. Every real-home application requires review of its exact root/role/state digest and separate operator approval. Legacy, preflight, direct-provider and Linux leases are unsupported; missing signed proof remains unknown and retained. Qualification is not permission to delete leases, quarantine, evidence or credentials.
